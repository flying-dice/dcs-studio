# Mission liveness is inferred from a socket that outlives the mission

[Issue #32](https://github.com/flying-dice/dcs-studio/issues/32), and the
in-source marker at `src/bridge/clients.ts:14-20`.

"A mission is running" is derived from `mission.connected` — a TCP socket's state
— by `combinedState`, `statusBarView` and `missionStartFailure` in
`src/core/domain/bridgeProtocol.ts:18-22`. But the mission bridge's server is a
process-wide Rust static that deliberately outlives the mission Lua state, so
after the user exits to the menu the socket stays open and `connected` stays
`true`.

The predicted symptom: the status bar reads "DCS: mission 843s" frozen at the
last mission's time, and F5 on a mission script is offered — queueing a
`debug_state` into a queue no pump will drain, so the user sees
`Mission bridge call 'debug_state' timed out` rather than "no mission running".

**Derived by reading both sides of the seam, not observed.** #32 asks for a
two-mission run to confirm before anything changes. Do it in the same live
session as card 03.

- **opus-verify** (2026-07-30T01:02:00.000Z): What this session *does* add, and it matters for the fix's shape more than the socket question does. **The card-18 teardown has changed #32's predicted symptom, in the direction of a better user experience but only for requests already in flight.** `bridge/crates/bridge-core/src/jsonrpc/server.rs:356` (`fail_queued`) now answers everything stranded in the queue at teardown with a JSON-RPC **`-32001` "bridge torn down"** (`bridge/crates/bridge-core/src/jsonrpc/mod.rs:24`), and it is not theoretical: the live runs failed **45** and **23** real queued requests at `S_EVENT_MISSION_END`, each of which would previously have sat until the 30 s server timeout and surfaced to the user as `Mission bridge call 'debug_state' timed out` — the exact string this card predicts. So for the in-flight case the diagnosis is now truthful. **But a request that arrives *after* teardown is a different story and is almost certainly still the silent timeout #32 describes:** the model-time pump unschedules itself once released (`bridge/crates/bridge-mission/lua/mission_init.lua:144-146` returns nil) and `fail_queued` only drains what was queued at that instant, so a later arrival queues into a server nothing will ever pump. I could not measure that end-to-end for the reason above, so I am flagging it as reasoned-from-code, not observed. It does mean the fix decision in checklist item 2 should **not** rest on `-32001` alone: gate on a fresh `dcsTime`/pump-liveness signal as this card and card 17 both argue, and note card 17's live finding that `GET /health` answers in 1–2 ms while `/rpc` cannot be dispatched at all — reachability really is not liveness, and now there is a measurement of that.
