# DCS crashes on every mission unload with the bridge deployed — is the bridge the cause?

Found while attempting card 04's two-mission run: this install **crashed on
every return from a mission to the main menu — three reproductions, three
different methods** (`DCS.stopMission()` via RPC, and QUIT through the UI
twice). The crash is what made card 04's verdict inconclusive.

It is not yet established that the bridge is the cause — but the mission DLL
stays loaded from first mission until process exit, its Lua state is being
torn down at exactly that moment, and teardown sampling showed the mission
listener dropping ~2.5 s before the GUI one with the process still alive. A
crash in a user's sim on every mission exit would be the worst bug this
project could ship, so cause-or-exoneration is the priority, ahead of
features.

First discriminator: reproduce the mission-exit path **with the bridge DLLs
and hook removed**. If it still crashes, this is an install problem and the
card closes with that evidence. If it stops, bisect: hook without mission DLL,
then mission DLL without an active debug session, then with one.

Check `Logs/dcs.log` tail and any crash dump under the write dir from the
card 03/04 session (2026-07-29 evening) before re-reproducing — the evidence
may already be on disk.

**Answered 2026-07-29: yes, the bridge is implicated.** Removed → clean twice;
restored → dead at t+10.6 s and t+10.9 s, with no debug session. Full evidence,
result table and mechanism in [issue #69](https://github.com/flying-dice/dcs-studio/issues/69).
A second defect surfaced during the bisect: a failed mission-bridge `require`
wedges the mission load permanently, also written up in #69.

**Discriminator closed 2026-07-29: the trigger is the mission bridge, not live
RPC re-entry.** With the mission-bridge boot suppressed (and the GUI bridge plus
the editor's live polling left exactly as they were), two unloads — including two
missions in one process — completed cleanly through the whole menu rebuild; with
it booted, the same build died at Stop+8.9 s. The fix belongs in the mission
bridge's teardown of the mission Lua state, not in quiescing the GUI pump.

- **opus-teardown** (2026-07-29T23:15:00.000Z): What the same read *did* turn up is a concrete hazard in the same window, and it is the one the card's instinct ("release everything the mission bridge holds in the mission state BEFORE that state dies") is right about. The only mlua handles that outlive `Dispatcher: Stop` are held **inside** the mission state: `JsonRpcRouter.methods` is a `HashMap<String, LuaFunction>` (`bridge/crates/bridge-core/src/jsonrpc/router.rs:49-62`), one live registry reference per registered method, reachable from the model-time pump closure and `DBG.pump` (`bridge/crates/bridge-mission/lua/mission_init.lua:126-152`). Nothing dropped them. They were dropped by the router userdata's `__gc` — and Lua 5.1 runs `__gc` **during** `lua_close`, so every one of those drops handed a registry reference back to a state already tearing down, in an order Lua does not define relative to mlua's own registry bookkeeping. That is the *only* place the mission bridge reaches into a dying state, it exists only for the mission DLL (the GUI state is never closed before process exit), and it fits the evidence: heap damage done inside `lua_close` surfaces later, non-deterministically, during the menu scene rebuild, violently enough to take DCS's SEH handler with it — which is exactly the signature of all seven deaths. **Stated at the confidence it deserves: a code-grounded hypothesis, not a proof.** No dump exists to confirm it and I did not go near DCS.
- **opus-teardown** (2026-07-29T23:25:00.000Z): **Fix shape — release while the state is whole, and leave `__gc` nothing to do.** New module `bridge/crates/bridge-core/src/jsonrpc/teardown.rs`, with two triggers because neither is sufficient alone. (1) `release()` (`bridge/crates/bridge-core/src/jsonrpc/teardown.rs:78`) drops every handler via `JsonRpcRouter::release` (`bridge/crates/bridge-core/src/jsonrpc/router.rs:94`) and then fails every queued request via `server::fail_queued` (`bridge/crates/bridge-core/src/jsonrpc/server.rs:356`), which answers each stranded caller a JSON-RPC `-32001` "bridge torn down" naming the cause (`bridge/crates/bridge-core/src/jsonrpc/mod.rs:24`) instead of leaving it to the 30 s server timeout or a bare closed channel. It is driven from the mission state's own `S_EVENT_MISSION_END` handler (`bridge/crates/bridge-mission/lua/mission_init.lua:103-120`) — the one point where the state is still fully functional — and also parked as `__DCS_STUDIO_MISSION_TEARDOWN` (`bridge/crates/bridge-mission/lua/mission_init.lua:97`) so it can be triggered by name. (2) `StateGuard` (`bridge/crates/bridge-core/src/jsonrpc/teardown.rs:99-126`), a sentinel userdata parked in `__DCS_STUDIO_MISSION_GUARD` (`bridge/crates/bridge-mission/lua/mission_init.lua:122`) whose destructor mlua runs from `__gc`, i.e. from inside `lua_close` — the backstop for a mission that never fires its end event.
